# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Discord bot for the Fjormcord community, built on discord.py (2.x) with a SQLite database. Features: character "art pings" (users subscribe to characters and get mentioned when art of them is posted), a gacha-currency wallet/scoreboard, and a scheduled Fire Emblem Heroes Coliseum closing reminder. Every command exists twice: as a `~` command and as a slash command. The user-facing command list lives in `README.md`.

## Commands

```bash
.venv/Scripts/python -m pip install -e ".[dev]"     # editable install with test dependencies (pyproject.toml)
.venv/Scripts/python -m fjormcord.bot.artping        # run the bot (exits unless config.ini sets discord.token); also: artping-bot
.venv/Scripts/python -m pytest                       # run all tests
.venv/Scripts/python -m pytest tests/fjormcord/bot/artping/service/test_art_ping_service.py::test_add_and_remove_ping   # single test
```

To reset a local database, delete the file; it is recreated on the next start.

Without the editable install, run with `PYTHONPATH=src`. Use `-e` rather than a plain `pip install .`: `config.py` locates the config files relative to its own file in `src/`, which breaks once the code is copied into `site-packages`. There is no linter configured.

## Layout

`src/` layout: all code is in the `fjormcord.bot.artping` package under `src/fjormcord/bot/artping/`. `fjormcord/` and `fjormcord/bot/` are PEP 420 namespace packages — they deliberately have **no `__init__.py`** (don't add one), so other distributions can share the `fjormcord` namespace; `artping/` is a regular package. Paths below are relative to `src/fjormcord/bot/artping/`.

Tests live in `tests/fjormcord/bot/artping/`, mirroring the source tree (e.g. `tests/fjormcord/bot/artping/service/` ↔ `src/fjormcord/bot/artping/service/`, and likewise `legacy/`, `legacy/handler/` and `slash/`); repositories are covered by the service tests, so `repository/` and `model/` have no test directory of their own. Shared fixtures and fakes stay in `tests/` itself. Test directories only have an `__init__.py` where they contain Python files, so `tests/fjormcord/` and `tests/fjormcord/bot/` have none. pytest therefore imports the test modules as `artping.…` (e.g. `artping.service.test_currency_service`); never add a top-level `artping` package, or it would collide. pytest finds the package via `pythonpath` in `pyproject.toml`, so tests run without installing.

## Configuration

The bot reads only `config.ini` (gitignored, in the repository root), which holds the real token and every setting; production edits it by hand. There are no defaults: a missing file or setting stops the bot at startup with a message. `config.example.ini` (committed) is a complete example of it, to copy: an empty `discord.token`, `discord.guild_id` (empty; development only, see Slash commands), `database.path` (`test.db`), `commands.cooldown_seconds` (`1`), `art_ping.slash_max_characters` (`10`; 1-25, the number of character options of `/artping`), `character_vote.votes_needed` (`5`) and `character_vote.emoji` (`⭐`; the file is read as UTF-8), `tasks.coliseum_notification_channel_id` (empty: no Coliseum reminders), and custom emoji IDs under `[emoji]`. The bot exits with a hint when no token is set. `config.py` locates `config.ini`, and resolves relative paths in it, against the repository root, so the bot can be started from any directory. It reads it once into a frozen `Settings` dataclass (`config.read_settings()`); other modules use its typed fields (`settings.coliseum_channel_id`) rather than section and key names. Adding a setting = the setting in `config.example.ini`, a `Settings` field, and its parsing in `load_settings`; tell the user to add it to production's `config.ini` too, or the bot won't start. Never put a token in `config.example.ini`.

The database file is gitignored. Tests need neither `config.ini` nor a database file: `tests/conftest.py` loads `config.example.ini` as the settings, so every test runs with the example's values whatever a local `config.ini` holds, and `test_config.py` checks the example is complete.

## Database migrations

The schema is defined only by the numbered scripts in `db/migrations/` (`001_initial_schema.sql`, `002_unique_names.sql`, ...); there is no separate schema file. `database.connect` applies every script numbered above the database's `PRAGMA user_version`, each in its own transaction together with the version bump, so a new database runs them all and the live one gets upgraded on its next start. `__main__` opens the database before connecting to Discord, so a failing migration stops the bot.

- To change the schema, add the next numbered script; never edit one that has been released, since the live database already ran it.
- `001` uses `CREATE TABLE IF NOT EXISTS` because the live database predates versioning (`user_version` 0, tables already present).
- Migrations run before `PRAGMA foreign_keys` is enabled: SQLite can't alter constraints, so changing one means rebuilding the table (create `NEW_X`, copy, drop `X`, rename), and with foreign keys on, dropping the table would cascade-delete its pings and wallets. The runner checks `PRAGMA foreign_key_check` before committing.

## Architecture

Layered: services, repositories and utilities are module-level functions; classes are used for state (`ArtPingClient`, `Cooldowns`), records (the dataclasses) and exceptions (`MissingArgument`, `CommandError`).

- `__main__.py` — entry point; sets up logging, checks the token, opens (and migrates) the database, sets intents (`message_content` is required) and runs `ArtPingClient`.
- `bot.py` — `ArtPingClient(commands.Bot)`: a `Bot` only to hold the cogs and the command tree; the `~` commands are not prefix commands (`command_prefix` is unused, `help_command=None`, `process_commands` is never called). `setup_hook` adds the cogs and syncs the slash commands; `on_ready` starts the Coliseum reminder; `on_message` hands every message to `legacy.dispatch.handle_message`. The client's `Cooldowns` (`cooldowns.py`, in memory, with an injectable clock) serve both syntaxes: one cooldown per user, `commands.cooldown_seconds` long, for every command (posting a resource included), so after any command a non-admin can't use another one until it runs out; which command it was isn't tracked. Easter egg replies and vote clicks are not commands.
- `legacy/` — the `~` path, kept as it was: `commands.py` (the `COMMANDS` table, `Command`, `format_usage`, `~help`), `dispatch.py` (`handle_message`: ignores messages from bots, this one included, so no bot can make it spam; sends easter egg replies; looks the first word up in `COMMANDS_BY_NAME`, case-insensitive and exact; silently ignores `admin_only` commands from non-admins; calls the handler and sends the returned string; handler exceptions are logged and answered with a generic failure message; the cooldown is checked here, also before posting a resource: a user still cooling down is turned down with a `CommandError` (`Cooldowns.check`), admins are exempt, and only a handler that succeeded starts the cooldown, so a command that was turned down can be retried right away) and `handler/<feature>_handlers.py`, the handlers that parse the message.
- `slash/` — the slash commands, one cog per feature (`ArtPingCog`, `CharacterCog`, `CurrencyCog`, `ResourceCog`, `EasterEggCog`, and `CharacterVoteCog`, which has no commands: the vote button and the vote listeners `on_ready` and `on_raw_message_delete`, raw so they also fire for messages sent before a restart; errors in them are logged, there is no one to reply to). `runner.run(interaction, name, call, ...)` is how every command answers, the slash counterpart of `legacy.dispatch`: admin check (for commands declared with `runner.admin_command`, which adds `default_permissions(administrator=True)` and `guild_only`; `run` reads the command's `default_permissions`, and checks again since server admins can change who sees a command), cooldown, the call, a `CommandError` as an ephemeral reply, other exceptions logged and answered ephemerally, long replies split. `defer=True` defers first for commands that wait on Discord; after a defer the replies, errors too, follow the defer's visibility. `options.py` holds `to_name` (spaces in a slash option become underscores) and the autocomplete callbacks (matched by prefix, at most 25 choices). `sync.py` registers the commands with Discord, see Slash commands. `/artping` is built by `build_art_ping_command(max_characters)`, one option per character up to `art_ping.slash_max_characters`.
- `vote_view.py` — `VoteView`, the persistent vote button (see Character votes).
- `easter_eggs.py` — the custom-emoji replies to whole messages such as "thanks lorenz" and "chromk" (`EASTER_EGG_REPLIES`, emoji from the `[emoji]` config section); `legacy.dispatch` sends them before command dispatch, and `/lorenz` and `/chromk` reply with the same constants.
- `coliseum.py` — the Coliseum closing reminder: a module-level `tasks.loop` (times in UTC) that `start_coliseum_notification(client)` starts with the client, once, and only when `tasks.coliseum_notification_channel_id` is set.
- `legacy/commands.py` — the `COMMANDS` table. Each `Command` holds its name, handler, help text/usage, help section and `admin_only` flag; `~help` is generated from it (admin commands only shown to admins). Keep the list grouped by section with admin-only commands last.
- `service/` — one module per feature, holding the logic. The rule: **services take typed arguments, legacy handlers parse messages, cogs read options** (and pass them through `slash.runner.run`). A service function takes what the command needs (`add_ping(user_id: str, name: str)`, `set_currency(user_id, name, amount: int)`), contains every check and reply, and returns the reply string, directly or as a coroutine (only the functions that wait on Discord, to resolve usernames or send and edit vote messages, are `async`); it never sees a message or interaction. Three replies name a command to use next (`check_wallet`, `get_scoreboard`, `list_resources`), so they take `slash=False` and answer with the slash form when it is `True`. Services reject a command by raising `CommandError(message)` (in `message_util`; logged as a warning and sent as the reply, ephemeral for slash); `require_character` / `require_currency` (in their services) look a name up or raise "… doesn't exist". The legacy handlers (`legacy/handler/*_handlers.py`) have the signature `handler(client, message)` and do only what is `~`-specific: `get_single_name(content, "character name")` for commands that take exactly one name and `get_two_entries(content, "currency name", "amount")` for those that take exactly two, and `MissingArgument("character name")` when a required argument is missing (answered with "Character name is missing. Usage: …", formatted from the command's `usage` tuple by `format_usage`, the same formatter `~help` uses), then call the service. Both live in `message_util`. Argument-count and format errors belong to the handlers; range and existence checks belong to the service, so both syntaxes get them.
- Adding a command = a service function + a legacy handler and its `Command` entry in `COMMANDS` + a slash command in its cog. `tests/fjormcord/bot/artping/slash/test_parity.py` fails when a legacy command has no slash command of the same name or the other way around (apart from `~help` and the slash-only `/resource`, `/lorenz` and `/chromk`), and `test_descriptions.py` checks Discord's description limits. Slash descriptions adapt the legacy ones (100 characters at most).
- `repository/` — raw SQL against SQLite through the single shared connection from `database.get_database_connection()`. Only the repository touches column names: it returns the `model/` dataclasses, plain values, or a `bool` from the `has_…` checks, so services use attributes like `character.id`. A query that returns a model aliases its columns to the field names (`SELECT C.CHARACTER_ID AS id, C.NAME AS name`) and builds it with `Character(**row)`; a single-column query unpacks its rows (`[user_id for (user_id,) in rows]`). Lookups return `None` when nothing is found. A single write goes through `database.execute(sql, parameters)`, which commits it, and a `has_…` check through `database.exists`; several writes that belong together share one `with get_database_connection() as conn:` transaction. Database errors are not caught here — they propagate to the client's generic handler. Character and currency names, and aliases, are `UNIQUE COLLATE NOCASE`, so a plain `NAME = ?` already matches case-insensitively (and uses the index); don't wrap them in `LOWER(...)`.
- Aliases: `character_repository.get_character` matches a character's name or any of its aliases, so every command that takes a character name accepts an alias and replies with the name. A name is either one character's name or one alias, never both: the database only enforces uniqueness within each table, so `character_service.require_unused_name` checks across them before adding a character or alias. `~setprimaryname` swaps an alias with the name in one transaction (`alias_repository.set_primary_name`).
- Name casing: character names and aliases are normalized with `name_util.normalize_name` (each part split on `_`, `!` or `'` capitalized, the rest lowercase) when the services read them from a message, so they are stored, and echoed in replies, that way. `database.connect` registers it as the SQL function `NORMALIZE_NAME` for migrations (`004` normalized the existing names). Currency names are not normalized.
- Character votes: a non-admin's `~addcharacter` or `/addcharacter` runs the usual checks, then (unless `votes_needed` is below 2, which turns voting off so everyone adds directly) `character_vote_service.start_vote(vote_channel, proposer_id, name)` sends the vote message itself, with the Vote button (the vote is stored by its message ID, in `CHARACTER_VOTE`), and the service returns `""`, which sends nothing more. `model.character_vote.VoteChannel` is what a syntax hands over for that: the channel ID, whether it is in a server, and a `send(content, view)` coroutine (legacy sends to the message's channel, slash as a follow-up of the deferred interaction with `wait=True`). A click on the button (`vote_view.VoteView`, persistent: fixed `custom_id`, no timeout, registered with `bot.add_view` by `CharacterVoteCog`, so every vote message works after a restart) first defers ephemerally, then `toggle_vote` adds the clicker's vote or takes it back and the clicker gets an ephemeral confirmation; the label shows the count. Voters are stored in `CHARACTER_VOTE_VOTER`, since a button keeps no list. At `character_vote.votes_needed`, or when an admin clicks, the character is added, exactly the stored voters are subscribed and every vote for the name is closed, in one transaction (`character_vote_repository.pass_vote`). The other vote messages for the name are edited to say so and lose their button, as are all of them when an admin adds the character directly. A vote whose message is gone, or whose name got taken another way (an alias), is dropped when checked or clicked; on `discord.Forbidden` it is kept. Votes don't expire. Migration `007` added the voters and `CHARACTER_VOTE.USES_BUTTON`: at startup `check_open_votes` converts each vote with `USES_BUTTON = 0` (a ⭐ vote from before the button) once, storing the users (bots excluded) who reacted with `character_vote.emoji` as voters and giving the message the button; that is the only place reactions are read, and `character_vote.emoji` is otherwise the button's emoji (the bot no longer needs Add Reactions). At every startup `check_open_votes` also re-renders the message of each vote that stays open (the current text and `VoteView(count)`), so it follows a changed `votes_needed`, and a conversion whose edit failed gets its button on the next start. `character_service` and `character_vote_service` import each other, so both import the other as a module (`from …service import character_vote_service`), never names from it.
- Resources: `~setresource hof <link>` (admin) stores the text of a linked Discord message, fetched once with `client.get_partial_messageable`, or a website link itself, in `RESOURCE`; `~hof` posts it. `legacy.dispatch` looks a word up in `COMMANDS_BY_NAME` first and only on a miss in the resources (`resource_service.get_resource_content`), so a command always wins, and `set_resource` refuses command names; it imports `legacy.commands` inside the function, since the legacy modules import the services. Resource replies (`~name` and `/resource`) are sent with `AllowedMentions.none()`, as the copied text may mention users. Names are ASCII letters, digits, `_` and `-`, not normalized, matched ignoring case.
- `model/` — the frozen dataclasses the repositories return, one module per feature (`character.Character`; `character_vote.CharacterVote`, and `VoteChannel`, which the services get instead of a message; `currency.Currency`, `WalletEntry`, `ScoreboardEntry`; `resource.Resource`). They hold data only and import nothing from the project. Dataclasses are kept apart from the code that uses them, so a new one goes here too; the exceptions are `Command`, which stays in `legacy/commands.py` next to the `COMMANDS` table, and `Settings`, which stays in `config.py` next to the code that loads it.
- `util/` — message handling (`message_util`: whitespace-split arguments after the command word, `CommandError`, and `split_message`, which `legacy.dispatch` and `slash.runner` use to keep replies under Discord's 2000-character limit) names (`name_util.normalize_name`, see Name casing above) and users (`user_util.is_administrator`, which lives here rather than in `commands.py` so services can use it without a circular import; `user_util.get_username`: the client's cache first, a Discord request only on a miss; never raises — look users up only for what is shown, e.g. one scoreboard page).

The connection enables `PRAGMA foreign_keys`, which the schema's `ON DELETE CASCADE` relies on (removing a character/currency removes its pings/wallets). Tests swap in an in-memory database built by `database.connect(":memory:")` via `set_database_connection` (autouse fixture in `tests/conftest.py`); fake messages, a fake client (with channels whose sent messages can be reacted to with `react` and edited) and a `FakeClock` (pass it to `Cooldowns(seconds, clock)` and move it with `advance`; the fake client's cooldown is 1 second) are in `tests/fakes.py`, along with `reply(handler, client, message)`, which runs a legacy handler as the bot does (awaiting it, and turning a `CommandError` into its message), `FakeInteraction` (response and follow-ups) with `invoke(command, interaction, cog=None, **options)`, which runs a slash command's callback, and `click(client, message, user_id, administrator=False)`, which presses a vote message's button.

Schema (`db/migrations/`): `CHARACTERS`, `ALIAS` (other names for a character), `PINGS` (character ↔ user ID), `GACHA_CURRENCY`, `GACHA_CURRENCY_WALLET`, `CHARACTER_VOTE` (open votes: message, channel, name, proposer, `USES_BUTTON`), `CHARACTER_VOTE_VOTER` (vote message ↔ user ID, cascades with the vote; migration `007`), `RESOURCE` (name, posted content, source link). Users are stored as Discord user ID text and rendered as `<@id>` mentions.

The `~` commands stay a hand-rolled dispatch (`legacy/dispatch.py`) on purpose: they are kept exactly as they were for the users who prefer them, while the slash commands are `discord.ext.commands` cogs.

## Slash commands

The commands are synced on every start (`slash.sync.sync_commands`, called from `setup_hook`); a failure (`discord.DiscordException`, `OSError`, `asyncio.TimeoutError`) is logged and swallowed, so the bot still runs with the `~` commands. `discord.guild_id` is for development only: it registers the commands in that one server, where they appear at once, and clears the global copy; production leaves it empty and syncs globally. The bot must be invited with the `applications.commands` scope. The README explains clearing commands left in a guild. Changing `art_ping.slash_max_characters` needs a restart, since the options are part of the registration.
